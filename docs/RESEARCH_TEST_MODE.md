# Participant Test Mode (`/test`)

An unmoderated, task-based usability test of the real Ana prototype. Participants use Ana itself; a
quiet test layer gives them one task at a time, notices when they succeed, and collects short feedback.
Everything is stored through the research data system (docs/RESEARCH_DATA_SYSTEM.md).

- **URL:** `https://<deployment>/test`. On a static preview, `?test` works too. An optional
  researcher-assigned code: `/test?p=P014`. The Production House study (when active): `/test?type=house`.
- **Code:** `src/research-data/TestMode.tsx` (flow), `src/styles/test-mode.css`, `src/research-data/surface.ts` (routing flags).
- **Not exposed:** the prototype console, persona switcher, Advanced, Edge Case Lab, QA tools,
  researcher controls and debug information. `?lab`, `?scenario`, `?specimen` and `?motion` are ignored
  on `/test`, exactly as in Research Mode.

## Layout rule: research UI never sits inside the phone

The simulated Ana phone renders exactly as it does outside `/test`: the same size (417 × 876 framed on
large screens), the same status bar, header, content and navigation. Nothing belonging to the study is
drawn inside the device, so participants can always tell **Ana** from **the research controls**.

- **Large screens (800 px and wider):** the phone, with a compact floating research panel beside it
  (300 px; warm paper, hairline border, soft shadow, 20 px radius, Ana green for the primary research
  action). The panel holds everything: the task card, Task details, Feedback, I'm stuck, the task
  questions, skip and end.
- **Small screens (under 800 px):** during an active task, a compact bar attached to the browser
  viewport below the device: `Task 2/6 · Find someone…`, plus Feedback and I'm stuck icon buttons, and
  **Done** only on tasks without an automatic success event. Tapping the task, or any research step,
  opens a sheet attached to the **browser viewport**, never to the simulated phone. On phone-width
  screens the device takes the viewport height minus the bar, constant for the whole session, so Ana
  never shifts.
- Between tasks and while answering task questions, the phone stays visible but is not operable
  (`inert`, shown at reduced opacity), so nothing leaks into the next task.
- Intro, consent, details, survey and thank-you are research pages shown on their own, with no phone.
- Verified on Home, Discover, Role Detail, Profile, Post Detail and the Create sheet, at desktop and
  phone sizes. There were zero research elements inside the phone, the status bar was present, and on
  desktop nothing overlapped the phone screen; the phone matched the normal prototype size exactly. On
  phone size the active-task bar sits fully below the device; only the research sheet (task questions,
  feedback, stuck), which is attached to the browser viewport, covers part of the inert phone.

## Participant flow

1. **Intro.** "Ana user test. Thanks for helping us test Ana. This is a prototype, so some things may not
   work yet. We're testing the product, not you. There are no wrong answers." Plus the expected length.
2. **Consent** (see below). Continue is disabled until the box is ticked.
3. **A little about you.** All optional: first name, craft (a short list), experience band. No email,
   phone or demographics. The participant code (P001...) is generated by the server and never shown.
4. **Session starts** (`POST /api/research/session`): the participant row (with `consented_at`), the
   session (study, prototype version, persona `kiran`, device), and the study's tasks.
5. **Task intro** (in the panel): "Task 2 of 6", the title and the instruction, then **Start task**
   (primary) or **End test**. Only the current task is shown; later tasks are never listed.
6. **Active task.** Ana is fully usable. The panel shows the task and instruction with **Task details**
   (instruction plus Skip this task), **Feedback** and **I'm stuck**, and End test as a text action.
   **I've finished this task** (or **Done** in the small-screen bar) appears only on tasks without an
   automatic success event (task 1, "Understand Home").
7. **Task questions** (the panel turns into "Task completed" after success, see "Success detection").
8. Repeat for every task, then the **final survey**, then the **thank-you** screen.

The study is chosen by participant type: the newest *active* study of that type
(`GET /api/research/study`). One session holds one study's tasks; the two task sets are never mixed.

## Consent copy

> **Before you start**
> - We record what you do in the prototype (screens you open, actions you take) to improve Ana.
> - Anything you choose to write in feedback is stored with it.
> - We never capture passwords or private messages, and nothing you type into the prototype itself.
> - You can stop at any time. What you've done so far is kept.
>
> ☐ I understand and agree to take part.

The session API refuses to start without `consent: true`. The server stores `consented_at`.

## Task model

- Tasks come from `research_tasks` for the study, in `sequence` order, with `success_events`.
- Research UI uses Ana's tokens (paper, hairline, Ana green for the one primary action, existing type),
  but always outside the device (see "Layout rule").

## Success detection

- While a task is active, Test Mode subscribes to the research client's semantic events. When an
  event matches the task's `success_events` (and `success_object_type`, if set), the task has succeeded.
- **Never mid-action:** the panel only turns into the task questions after Ana's own sheet has closed
  (for example the Show Interest sheet after Send), then about 1.1 s more for the transition to settle.
  The phone is never replaced.
- The server marks `success_detected` independently from the same events.
- Seeded tasks: understand Home (no event: Done), find someone in your craft (`person_profile_opened`),
  find posts (`post_opened`), save a project or role (`project_saved`, `role_saved`), show interest
  (`interest_sent`), your profile (`own_profile_viewed`).

## Task feedback

After each task: "How easy or difficult was that?" on a scale of **1 very easy to 5 very difficult**;
"Was this what you expected to happen?" Yes or No; if No, "What were you expecting?" (optional);
"Was anything confusing?" (optional).

Stored on the attempt:
- `difficulty_rating` (1–5);
- `expectation_match` (Yes = 5, No = 1, using the existing 1–5 column);
- `feedback_text` (`Expected: …` and `Confusing: …` lines).

## Outcome rule

| Situation | Outcome |
|---|---|
| Success (detected, or Done on a task without a success event) and difficulty 1–3 and I'm stuck not used | `completed` |
| Success, and difficulty rated 4–5 **or** I'm stuck used during the attempt | `completed_with_difficulty` |
| Skip task (directly or from I'm stuck) | `skipped`, with the duration and the optional reason in `feedback_text` |
| End test while a task is open | `abandoned` (closed by the server when the session is completed as abandoned) |

Skipped is never counted as success.

## Feedback button

**Feedback** (in the panel, or the viewport sheet on small screens; never a modal inside Ana) → a
category:
- Something was confusing
- I couldn't find something
- Something looked wrong
- Something didn't work
- I have a suggestion
- Other

Then an optional comment, then Send; the panel returns to the active task with "Thanks, your feedback
was sent." Context is attached automatically and the participant is told
so ("We'll know which screen and task you were on"): session, task attempt, current screen, persona,
build (copied from the session by the server), timestamp, and the event position
(`trail_until_sequence`). The trail itself is derived from `research_events` later and is not copied
into the feedback row. Stored with `interaction_context.source = 'button'`.

## I'm stuck and skip

- **I'm stuck** (in the panel or the bar) records `stuck_reported` and asks "What are you trying to do?"
  (optional). Then: **Continue trying** or **Skip task**. A comment is stored as feedback (category
  `couldnt_find`, `source = 'stuck'`). The correct path is never revealed: we are testing findability.
- **Skip task** asks for an optional reason, records `outcome = skipped`, and moves to the next task.

## Ending early

**End test** (from the task intro or the active task panel) asks for confirmation: "Your answers so far will be
kept." The session is completed as `abandoned`. Completed attempts keep their outcomes and the open one
becomes `abandoned`. The participant sees a thank-you screen; nothing is discarded.

## Final survey

1. Overall, how easy was Ana to understand? (1–5, **1 very difficult, 5 very easy**)
2. What do you think Ana is for? (free text)
3. What was the most confusing part? (optional)
4. What, if anything, would make you want to use Ana? (optional)

No schema change was needed. Each answer is a `research_feedback` row with category `other`,
`interaction_context.source = 'survey'`, `question` (`overall_ease`, `what_is_ana_for`,
`most_confusing`, `would_make_you_use`) and, for question 1, `rating`. The dashboard shows them under
"Final survey" and keeps them out of the feedback inbox. A dedicated survey table is a possible later
refinement.

## Session resume

The research client keeps the session token in `sessionStorage` (per tab). Test Mode keeps its stage
and task index there too. A reload or reopening in the same tab resumes at the same step, for example
"Task 4 of 6", and an open attempt is reused, not duplicated. Verified by reloading mid-test. The
prototype's own state (saved items etc.) starts fresh on reload, as it always does. A new tab, or a
closed browser, starts a new session.

## Privacy

- Only semantic events are recorded (docs/RESEARCH_DATA_SYSTEM.md, "Event taxonomy"). Nothing typed
  into the prototype itself is stored: no message text, search text or form contents.
- The only participant words stored are the ones the test asks for: task answers, feedback comments,
  the stuck note, the skip reason and survey answers.
- No email, phone or demographics. The name is optional and shown to researchers only as secondary
  to the participant code.

## Isolation

- The normal prototype and the existing `?research` mode record nothing. Verified: 0 requests,
  0 sessions, 0 events.
- A token left in a tab only counts on the surface that started or resumed it. Opening the normal
  prototype in the same tab after a test records nothing; the client stays inactive.
- `/test` is the only participant surface that starts sessions. Existing Research Mode (`?research`,
  moderated, Aditi for Konark) is unchanged and separate.
